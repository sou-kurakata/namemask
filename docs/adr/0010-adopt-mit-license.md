# ADR-0010: ライセンスに MIT を採用する

- **Status**: Accepted
- **Date**: 2026-07-30

## Context

v0.1.0 を PyPI に公開するにあたり、ライセンスを確定する必要がある。
決定の時点で分かっていた制約は次の4つ。

1. **利用者は企業の中の人。** このツールが解く問題は「取引先名や担当者名を含む
   業務文書を外部AIに投げたい」であり、想定利用者は勤務先の情報管理規程の下で
   ツールを選ぶ。法務レビューを通しやすいこと、そこで止まらないことが
   採用の前提条件になる。
2. **組み込み利用が主要な使い道。** namemask は単体の完成品ではなく、
   `mask()` / `unmask()` を自社のスクリプトや社内ツールから呼ぶライブラリとしても
   使われる（`api.py` が公開インターフェース）。実際にこのプロジェクト自身が、
   別リポジトリ `namemask-app`（private）から PyPI 経由で依存する構成をとる（ADR-0011）。
3. **依存ライブラリのライセンスは寛容型。** ランタイム依存は PyYAML（MIT）と
   pyahocorasick（BSD-3-Clause）の2本だけ。コピーレフトの依存が無く、
   ライセンス選択が依存側から制約されていない。
4. **法務・ライセンス運用の体制が無い。** 開発は個人（`sou-kurakata`）。
   CLA の管理、デュアルライセンスの個別交渉、コピーレフト違反の追跡といった
   継続的な運用コストを払える前提が無い。

なお本プロジェクトの価値の中心は**辞書や学習済みモデルではなく、検出パイプラインの
コードと golden corpus** にある（`tests/golden/corpus.json`。実在データは含まない。
`CLAUDE.md` §8）。「データを囲い込むためにコードを縛る」という動機が存在しない。

## Options considered

### (A) MIT

- 利点: 最も広く知られた寛容型ライセンス。企業の法務レビューで定型処理される。
  組み込み・改変・再配布を明示的に許す。全文が短く、条文の解釈で揉めない。
- 欠点: 改変版を非公開のまま配布できるため、改善が上流に戻る保証がない。
  特許条項が無い。

### (B) Apache-2.0

- 利点: 明示的な特許許諾（第3条）と、商標の扱いの明文化がある。
  企業からの貢献を受け入れる際の法的な確度が MIT より高い。
- 欠点: 条文が長く、`NOTICE` ファイルの取り回しなど再配布側の義務が増える。
  この規模のプロジェクトが得る保護に対して、利用者側の確認コストが割に合わない。
  namemask には防衛したい特許が無い。

### (C) GPL-3.0 / AGPL-3.0（コピーレフト）

- 利点: 改変版の公開を強制でき、改善が上流に戻りやすい。
  商用の囲い込みに対する抑止力になる。
- 欠点: **想定利用者の環境で採用が止まる。** 社内ツールに組み込む用途で
  「派生物の扱い」を法務が判断できず、検討の入口で落ちる可能性が高い。
  AGPL ならネットワーク越しの利用にも義務が及ぶが、namemask は
  完全ローカルが不変条件（`CLAUDE.md` §2-3）なのでそこに守る対象が無い。
  さらに、この構成では `namemask-app`（private・非公開の派生的利用）が
  自プロジェクト内で成立しなくなる。

### (D) 独自ライセンス / 非商用条項付き

- 利点: 商用利用を個別に交渉できる。
- 欠点: OSI 承認外なので「OSS」として扱われない。PyPI の classifier に載らず、
  企業の許可リスト（OSI 承認ライセンスのみ可）を通らない。
  条文の解釈と交渉を継続的に自分で背負う。

## Decision

**(A) MIT を採用する。**

判断基準は「**このツールが実際に使われるか**」の一点。namemask の目的は
検出漏れによる情報漏洩を減らすことであり、法務レビューで止まって導入されなければ
精度がいくら高くても目的を達しない。MIT は利用者側の確認コストが最小で、
組み込み利用（制約2）を条件なしに許す。

- **(B) を却下した理由**: 得られるのは主に特許条項だが、防衛したい特許が無く、
  企業からの大規模な貢献も現時点で想定していない。増える再配布側の義務
  （`NOTICE` の維持など）に見合う便益が無い。
- **(C) を却下した理由**: 想定利用者の採用障壁が最大の却下理由。加えて、
  コピーレフトが守ろうとする「ネットワークサービス化による囲い込み」は、
  完全ローカル・外部通信ゼロという不変条件がある本プロジェクトでは
  そもそも起きない。守る対象の無い制約は、コストだけが残る。
- **(D) を却下した理由**: OSI 承認外はライセンス運用の負担が最大で、
  体制が無い（制約4）。「OSS として公開する」というこのプロジェクトのゴールと矛盾する。

改変版が上流に戻らないリスクは受け入れる。**このプロジェクトの再現困難な資産は
コードではなく golden corpus と受け入れ基準**（`CLAUDE.md` §6）であり、
それは検出漏れの実例を集め続けることでしか作れない。ライセンスで守るものではない。

## Consequences

- `LICENSE`（MIT 全文・`Copyright (c) 2026 sou-kurakata`）、
  `pyproject.toml` の `license = { text = "MIT" }` と
  `License :: OSI Approved :: MIT License` classifier、
  `README.md` の badge と License 節、`CONTRIBUTING.md` の License 節が
  すべて MIT で整合している。**どれか1つを変える変更は全部を変える。**
- 貢献は **CLA なし**で受け入れる。`CONTRIBUTING.md` に
  「貢献した時点で MIT として提供したものとみなす」（inbound=outbound）と明記済み。
  署名の収集・保管という運用が発生しない。
- 著作権者表記は**実名を出さず GitHub ハンドル**（`sou-kurakata`）で通す。
  P0-2 で決めた匿名方針と一致させている。
- 派生プロジェクト（`namemask-app` を含む）を非公開のまま配布できる。
  これは (C) を却下したことの直接の帰結であって、抜け道ではない。
- **見直し条件**: ライセンスは実質的に一方向で、公開後に制約を強める変更は
  既存利用者の権利を取り消せないため意味を持たない。したがって
  「MIT からコピーレフトへの変更」は検討対象にしない。
  再検討の余地があるのは**特許条項が必要になったとき**（企業からの
  大規模貢献を受け入れる、または特許リスクの指摘を受ける）だけで、
  その場合の候補は Apache-2.0 への移行（＝全貢献者の同意が必要）である。
