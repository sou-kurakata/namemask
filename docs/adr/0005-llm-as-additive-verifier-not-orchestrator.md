# ADR-0005: LLM をオーケストレーターにしない（追加専用の検証者に限定）

- **Status**: Accepted
- **Date**: 2026-07-30 <!-- ADR として起こした日。原決定はプロトタイプ期（日付未記録） -->
- **Legacy ID**: ADR-005

## Context

「エージェントに文書を渡し、マスクすべき箇所を判断させ、ツールを呼ばせる」という
構成は取りうる。ローカル LLM（Ollama）が使える前提なら、完全ローカルという
不変条件3を守ったままでも実現できる。

一方でマスキングという処理は、エージェント化が向く形をしていない:

- 経路が固定されている。正規化 → 検出 → 統合 → 置換で、分岐がない。
- 各ステップの入出力が決まっている。「次に何をするか」を判断する余地がない。
- 失敗のコストが非対称（不変条件2）。

ここに非決定性が入ったときの最悪ケースは、精度の低下ではない。マスカーを呼ばない、
あるいは一部にしか適用しないという、気づかれないままの漏洩になる。

## Options considered

### (A) LLM をオーケストレーターにする（エージェントがパイプラインを駆動する）

- 利点: 新しいエンティティ種にコード変更なしで対応できる可能性がある。
- 欠点: 「マスカーを呼び忘れる」「一部のチャンクだけ処理する」という失敗モードが
  存在してしまう。同じ入力で同じ出力が保証されない（不変条件4に反する）。
  LLM が落ちるとツール全体が動かない。

### (B) LLM を検証者に限定し、スパンの追加のみ許可する

- 利点: 最悪ケースが「過剰マスク（軽微）」に固定される。決定的層の結果が
  常にそのまま残り、LLM が落ちても壊れない（fail-safe）。
- 欠点: LLM が「これは誤検出だ」と判断しても解除できない。
  分岐のある処理を LLM に任せる将来の拡張がしにくい。

## Decision

**(B) を採用する。**

(A) を却下した理由は、得られる自由度に対して失う保証が大きすぎること。
マスキングは固定経路で分岐がないため、エージェント化の利得がそもそも小さい。
その小さな利得のために、「マスクが適用されないことがある」という失敗モードを
設計に招き入れることになる。

追加専用に閉じ込めれば、LLM がどれだけ誤っても結果は「余計にマスクされた」で
止まる。パースに失敗しても、Ollama が起動していなくても、タイムアウトしても、
決定的層によるマスクがそのまま出る。LLM は結果を良くすることはできるが、
悪くすることはできない。

この「統計的/生成的なものは追加専用」という思想は ADR-0003（NER を追加層に限定）と
同根である。

## Consequences

- `detectors/llm_verifier.py` は、まだマスクされていない語だけを LLM に見せ、
  追加分のスパンだけを受け取る。解除・変更の経路はコード上に存在しない
  （不変条件5）。
- 幻覚への防御も同じ場所に入っている。原文に存在しない文字列は破棄し、
  長すぎる表層（`_MAX_SURFACE_LEN = 40`）も捨てる。
- 失敗時の挙動は「このチャンクの追加をスキップして決定的結果を採用」。
  Ollama 不在・タイムアウト・JSON 破損のすべてで同じ（`tests/test_llm_verifier.py`）。
- LLM 層は optional extra で既定 off。送信先はループバック限定
  （不変条件8。`docs/security.md` T1）。
- 受け入れたトレードオフ: 誤検出の自動解除ができない。過剰マスクを削るのは
  人間のレビュー（`--html`）の仕事のまま（ADR-0004）。
- **見直し条件**: なし。この決定は不変条件4・5そのものであり、
  変えるならまず不変条件の議論になる。
