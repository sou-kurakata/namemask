# ADR-0004: score による関門を置かず precision を意図的に犠牲にする

- **Status**: Accepted
- **Date**: 2026-07-30 <!-- ADR として起こした日。原決定はプロトタイプ期（日付未記録） -->
- **Legacy ID**: ADR-004

## Context

検出器はスパンに確信度（`Span.score`）を付ける。ここには「どこで線を引くか」という
自由度がある。閾値を上げれば誤検出（過剰マスク）が減り、下げれば見逃しが減る。

この選択は不変条件2（失敗は非対称）で決まる。

- **見逃し**＝機密がそのまま外部 AI に渡る。取り返しがつかない。
- **過剰マスク**＝関係ない語がプレースホルダになる。文脈の情報が減るが、被害は軽い。

事後の扱いやすさも非対称である。過剰マスクは人間のレビュー（`--html`）と
ストップワード設定で後から削れる。見逃しはレビュー画面に現れないので削れず、
起きたこと自体に気づけない。

## Options considered

### (A) F1 が最大になる閾値を選ぶ

- 利点: 閾値の選び方が指標から機械的に決まる。恣意性が入らない。
- 欠点: F1 は見逃しと誤検出を同じ重みで扱う。このツールでは両者の損失が釣り合わない。

### (B) 閾値を低く取り、precision を意図的に犠牲にして recall を最大化する

- 利点: 不変条件2の損失構造と一致する。過剰マスクはレビューで回収できる。
- 欠点: 誤検出が増えると人間のレビュー負荷が上がる。マスク後テキストの
  可読性が下がり、外部 AI の応答品質にも影響しうる。

## Decision

**(B) を採用する。**

(A) を却下したのは、F1 の最適化が「見逃し1件と誤検出1件は等価」という前提に
立っているため。このツールではその前提が成り立たない。

実装は「閾値を低くする」より踏み込んでいて、パイプラインに score による関門を
そもそも置いていない。検出器が返したスパンは、統合層で重なりを解消されたうえで
すべて置換される。`Span.score` の用途は、同じ範囲を争うスパンのどちらを採るかの
順位付けだけである（`SOURCE_PRIORITY` と併用）。スパンを捨てる判定には使わない。

受け入れ基準（`CLAUDE.md` §6）が precision に ≥ 70% という緩い下限しか置かず、
recall 側に 100% / ≥ 98% / ≥ 95% と厳しい線を並べているのは、この決定の帰結である。

## Consequences

- 誤検出は「人間が `--html` のレビューで捨てるもの」という前提で設計されている。
  レビュー経路が無い使い方（`namemask mask` の出力を無検査で外部 AI に投げる）は
  この決定の想定外の運用になる。
- precision の下限 70% は許容値であり、目指す値ではない。実測は 1.00 で、
  recall を優先しても precision は落ちていない。
  precision を上げるために recall を下げる変更は入れない。
- `Span.score` は `pipeline/merger.py` の統合でのみ参照される。
  検出器ごとの値は `detectors/*.py` にリテラルで置かれている
  （regex / denylist / address = 1.0、structural = 1.0 / 0.9、llm_verifier = 0.4）。
- `config.yaml` の `ner.score_threshold` は、名前に反して関門ではない。
  NER 層が返すスパンに付与する `score` の値なので、上げ下げしてもスパンは
  捨てられず、統合時の優先順位が動くだけになる。
- **見直し条件**: 実運用で precision が受け入れ基準（≥ 70%）を割り、
  レビュー負荷が「見逃しリスクを引き受けてでも減らしたい」水準に達した場合。
  その場合も閾値ではなく、ストップワードのように理由を説明できる手段を先に検討する。
