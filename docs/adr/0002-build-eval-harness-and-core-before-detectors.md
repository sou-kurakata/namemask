# ADR-0002: 評価基盤とコアエンジンを検出器より先に作る

- **Status**: Accepted
- **Date**: 2026-07-30 <!-- 旧 Planv2.md §13 からの移設日。原決定はプロトタイプ期（日付未記録） -->
- **Legacy ID**: ADR-002

## Context

このツールの品質は2つの独立した軸で決まる。

1. **検出精度** —— 機密を取りこぼさないか（recall）。
2. **可逆性** —— `unmask(mask(x))` が原文を完全復元するか（不変条件1）。

2 は検出精度がどれだけ低くても満たせるし、逆に検出精度がどれだけ高くても壊れうる。
そして「精度」は測定手段がない状態では改善できない —— 検出器を書いても、
それが良くなったのか悪くなったのかを言えない。

## Options considered

### (A) 検出器を先に書き、動くようになってから評価基盤を用意する

- 利点: 早い段階で「マスクされたテキスト」という目に見える成果が出る。
- 欠点: 検出器の良し悪しを比較する基準が最後まで無い。可逆性のバグが
  検出精度のバグと混ざり、どちらを直しているのか分からなくなる。

### (B) golden corpus と eval スクリプト、置換・復元エンジンを先に作り、
検出器はスタブで代用する

- 利点: 可逆性を 100% に固定したうえで検出器の開発に入れる。以後の検出器の
  変更は recall / precision の差分として読める。
- 欠点: 最初のうちは「何もマスクしないツール」に見える期間がある。

## Decision

**(B) を採用する。**

(A) を却下したのは、可逆性のバグと検出精度のバグが同じ症状（復元後のテキストが
原文と違う）で現れるため。切り分けの手段を持たずに両方を同時に開発すると、
どちらの問題を見ているのか判断できない時間が長く続く。

具体的には、golden corpus の正解エンティティをそのまま返すスタブ検出器
（`detectors/stub.py`）を用意し、「検出は完璧」という条件下で置換・復元の
round-trip 完全一致を先に 100% にする。以後の実検出器は同じ Protocol
（`detectors/base.py`）を満たして差し替えるだけなので、round-trip の 100% は
検出器を入れ替えても壊れない性質として残る。

## Consequences

- `tests/golden/corpus.json`（99ケース）と `tests/eval.py` が
  検出器開発の基準線になっている。検出器を変える PR は eval の before/after を
  示せる（`CLAUDE.md` §6）。
- round-trip 完全一致 100% は golden 全ケースと hypothesis による property-based
  テストの両方で固定されている（`tests/test_roundtrip.py`）。
- スタブ検出器（`detectors/stub.py`）が本番コードとして残っている。
  テスト専用に見えるが、これは「可逆性を検出精度から切り離す」装置であり、
  検出器 Protocol の参照実装でもある。
- 評価基盤があることで、後の ADR-0003（決定的層で recall の床を作る）の
  アブレーション（層ごとの寄与測定）が可能になっている。
- **見直し条件**: なし。この決定は開発順序についてのものであり、すでに実行済み。
  記録として残す。
