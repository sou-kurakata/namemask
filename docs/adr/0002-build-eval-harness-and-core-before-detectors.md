# ADR-0002: 評価基盤とコアエンジンを検出器より先に作る

- **Status**: Accepted
- **Date**: 2026-07-30 <!-- ADR として起こした日。原決定はプロトタイプ期（日付未記録） -->
- **Legacy ID**: ADR-002

## Context

このツールの品質は2つの独立した軸で決まる。

1. **検出精度** —— 機密を取りこぼさないか（recall）。
2. **可逆性** —— `unmask(mask(x))` が原文を完全復元するか（不変条件1）。

2 は検出精度がどれだけ低くても満たせるし、逆に検出精度がどれだけ高くても壊れうる。
そして「精度」は測定手段がない状態では改善できない —— 検出器を書いても、
それが良くなったのか悪くなったのかを言えない。

## Options considered

### (A) 検出器を先に書き、動くようになってから評価基盤を用意する

- 利点: 早い段階で「マスクされたテキスト」という目に見える成果が出る。
- 欠点: 検出器の良し悪しを比較する基準が最後まで無い。可逆性のバグが
  検出精度のバグと混ざり、どちらを直しているのか分からなくなる。

### (B) 評価基盤とエンジンを先に作り、検出器はスタブで代用する

- 利点: 可逆性を 100% に固定したうえで検出器の開発に入れる。以後の検出器の
  変更は recall / precision の差分として読める。
- 欠点: 最初のうちは「何もマスクしないツール」に見える期間がある。

## Decision

**(B) を採用する。**

(A) を却下したのは、可逆性のバグと検出精度のバグが同じ症状（復元後のテキストが
原文と違う）で現れるため。切り分けの手段を持たずに両方を同時に開発すると、
どちらの問題を見ているのか判断できない時間が長く続く。

具体的には、golden corpus の正解エンティティをそのまま返すスタブ検出器
（`detectors/stub.py`）を用意し、「検出は完璧」という条件下で置換・復元の
round-trip 完全一致を先に 100% にする。以後の実検出器は同じ Protocol
（`detectors/base.py`）を満たして差し替えるだけなので、round-trip の 100% は
検出器を入れ替えても壊れない性質として残る。

## Consequences

- `tests/golden/corpus.json`（99ケース）と `tests/eval.py` が
  検出器開発の基準線になっている。検出器を変える PR は eval の before/after を
  示せる（`CLAUDE.md` §6）。
- round-trip 完全一致 100% は golden 全ケースと hypothesis による property-based
  テストの両方で固定されている（`tests/test_roundtrip.py`）。
- スタブ検出器（`detectors/stub.py`）が本番コードとして残っている。
  テスト専用に見えるが、これは「可逆性を検出精度から切り離す」装置であり、
  検出器 Protocol の参照実装でもある。
- スタブは golden corpus の正解をそのまま返すため、本番経路が誤ってスタブを
  選択した場合、コーパス外の入力に対して検出ゼロになる。このとき round-trip
  テストは全て緑のまま通る（置換が起きないので原文がそのまま復元される）。
  可逆性を検出精度から切り離したことの裏返しで、既存のテスト群だけでは
  この障害を検知できない。
- スタブが本番経路に混入しないことは、次の3つの実装上の性質に依存している。
  1. `pipeline/build.py` の層テーブルがハードコードされた dict で、`layers`
     引数は名前からクラスを引く検索ではなく既知層への絞り込みであること。
     本 ADR を書く過程で、絞り込みが未知名を黙って落とすため
     `layers={"reges"}` のような typo 一つで検出ゼロのパイプラインが
     作れることが判明し、未知名と空選択を `ValueError` にした。
     `make_pipeline(disabled=...)` の未知名も同様に例外にしている。
     こちらは黙って no-op するため検出は減らないが、eval のアブレーションが
     「この層を抜いても指標が変わらない」という偽の測定値を出す。
  2. 公開 API `mask_text` に検出器の注入口がないこと。`llm_client` は
     注入できるが、LLM 層は追加専用（不変条件5）でマスクを解除できない。
  3. 検出器を登録する entry_points が存在しないこと。

  これらは `tests/test_pipeline_stub_isolation.py` が固定している。層構成は
  「stub が入らない」という否定形ではなく完全一致で書いてある。否定形では
  パイプラインが空集合を返す退行を見逃すが、それはここで防ぎたい障害そのもの
  だから。
- stub は round-trip 検証のため単独で実行する用途しかなく、実検出器と同一
  パイプラインで競合する経路が存在しない。したがって `SOURCE_PRIORITY` に
  登録する理由がないため外した（未登録は `merger.py` の `.get(s, 0)` により
  単独最下位となる）。これは混入時の被害を減らす二次的な防御でもある。
- 評価基盤があることで、後の ADR-0003（決定的層で recall の床を作る）の
  アブレーション（層ごとの寄与測定）が可能になっている。
- **見直し条件**: 開発順序としての決定は実行済みで覆す余地はない。ただし
  スタブを本番コードに残すことの帰結は継続するため、以下のいずれかを行う
  場合は本 ADR の帰結を再検討する。
  - 層の動的解決（名前からクラスを引く仕組み）の導入
  - `mask_text` への検出器注入口の追加
  - entry_points 等のプラグイン機構の導入
  - スタブを実検出器と同一パイプラインで走らせる用途の発生
    （`SOURCE_PRIORITY` 非登録の前提が崩れる）

  `tests/test_pipeline_stub_isolation.py` は仕様の検証ではなく、上記を検知する
  ためのトリップワイヤである。前3項は直接、4項目めは `SOURCE_PRIORITY` への
  再登録として落ちる。テストを直す前にこの条件を読むこと。
