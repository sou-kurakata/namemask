# ADR-0001: 汎用PIIフレームワーク（Presidio等）を使わず薄い自前パイプラインにする

- **Status**: Accepted
- **Date**: 2026-07-30 <!-- 旧 Planv2.md §13 からの移設日。原決定はプロトタイプ期（日付未記録） -->
- **Legacy ID**: ADR-001

## Context

日本語のビジネス文書から取引先名・担当者名・連絡先・住所を検出し、可逆に置換して復元する
必要がある。この種の用途には Microsoft Presidio をはじめとする汎用 PII フレームワークがあり、
recognizer（検出器）と operator（置換器）を差し替える拡張点を持っている。

決定の時点で分かっていた制約:

- 対象は**日本語のみ**。既製 recognizer は英語圏 PII（SSN・US phone・英語人名リスト等）が前提。
- 要件は recall 最優先（不変条件2）で、**完全ローカル**（不変条件3）・**決定的**（不変条件4）。
- 想定コード規模は全体で千行規模。
- セキュリティツールなので依存の少なさそのものが価値になる。

## Options considered

### (A) Presidio 等の汎用フレームワークを土台にし、カスタム recognizer / operator を積む

- 利点: スパン統合・エンティティ型・匿名化 operator の枠組みが最初から手に入る。
  他言語へ広げるときに既製資産が効く。
- 欠点: 日本語では正規表現・辞書・NER・operator を**どのみち総カスタム**することになり、
  手元に残るのは抽象化レイヤの学習・追従コストだけになる。依存が増える。

### (B) 検出から復元までを自前で実装する

- 利点: 精度バグの大半が潜む場所（正規化オフセット・重複スパンの統合・置換順序）が
  自分のコードとして見え、診断とテストが速い。依存が最小になる。
- 欠点: 統合層・型体系・置換器を自分で持つ。多言語化したくなったら資産がない。

## Decision

**(B) を採用する。**

(A) を却下した理由は、フレームワークが引き受けてくれるはずの部分が日本語では
ほぼ残らないこと。既製 recognizer が英語圏 PII 前提である以上、正規表現層・構造ルール層・
辞書層・NER 層はすべて自前で書くことになる。それでもフレームワークを噛ませると、
**得るものが抽象化レイヤだけで、失うものが診断の速さ**になる。

とくに、このツールの精度バグはスパン座標処理に集中する —— 正規化した影テキスト上で
検出したスパンを原文座標へ戻す（不変条件6）、重なったスパンをどう統合するか、
どの順序で置換するか。ここをフレームワークの内部に隠されると、recall が落ちたときに
原因へ到達できない。全体が千行規模である以上、自前の方が監査性・テスト容易性で勝る。

依存を最小化できることはサプライチェーン面の利点でもある（不変条件3）。

## Consequences

- 統合層（`pipeline/merger.py`）・型体系（`types.py`）・置換器（`core/replacer.py`）・
  復元器（`core/restorer.py`）を自前で保守する。
- 検出器は `detectors/base.py` の Protocol を満たす薄いクラスとして足せる。
  スタブ検出器（`detectors/stub.py`）を差し込めるのもこの構造のおかげで、ADR-0002 の
  「可逆性を検出精度から切り離して先に固定する」が成立している。
- ランタイム依存は `pyahocorasick` と `PyYAML` のみに収まっている
  （NER / LLM は optional extras）。
- 多言語化の資産はない。日本語以外の PII 対応は現在スコープ外（`docs/design.md` §Scope）。
- **見直し条件**: 対応言語やエンティティ種が大きく増え、既製 recognizer 資産の
  再利用価値が抽象化レイヤのコストを上回った場合。
